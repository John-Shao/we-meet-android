## 0. TL;DR(结论先行)

| 问题 | 结论 |
|---|---|
| 能不能原生? | 管理、浏览、搜索、阅读和评论列表适合原生；正文编辑、评论锚点、版本恢复涉及 Yjs，保留 Web 协作编辑器。是否原生化以数据语义与可验证的收益决定，不能仅由 REST 接口存在决定。 |
| 为什么编辑最难? | 本地实现中 docs 的内容 = **base64 编码的 Yjs(CRDT)更新**,不是 JSON;编辑 = BlockNote 块编辑器 + Yjs 绑定 + Hocuspocus WebSocket 协同 + Awareness 光标/评论锚点。本项目没有已经验证的原生协作编辑器集成。自研需承担块模型、CRDT 绑定、协同协议和恢复语义，当前继续复用 Web 编辑器。 |
| 推荐路线 | **原生管理与快照阅读 + Web 协作编辑器**。列表、子文档、评论列表、分享、版本列表逐项原生化；编辑、版本恢复、评论锚点继续使用 Yjs 感知的 Web 实现。同库同账号是互通基础，数据格式、刷新和保存协议仍需实现并验收，不给未经测量的对齐百分比。 |
| 下一阶段 | 按发布阻断项 → 功能连续性 → 体验与性能推进，见第五节。旧的 82–114 人日是立项范围估算，不能作为已有实现之后的剩余排期。全原生编辑不列入当前路线。 |
| UX 规范 | **硬性要求,逐条映射**:《设计规范.md》(M3 + token + 组件 + 三态 + 文案 + 无障碍 + §7 清单 + `checkDesignTokens` 10 条护栏)与《app-ux-device-matrix.md》(横竖屏/字体缩放/折叠屏/insets/键盘)全覆盖;文档内容区样式走**新增语义 token + 对比度实算单测**,豁免边界限定在 renderer 包并注明理由(§4.11) |
| 后端改动 | 当前继续复用会话与业务 REST，不新增 ticket 明文字段。docs 前端必须补齐保存确认、评论兼容与刷新、指定版本和评论入口；仅增加 `chrome=editor` CSS 不构成完整编辑画布。 |
| 落地形态 | 新 `feature-docs` 模块(对标 `feature-im` 的模块划分与实现范式),接入 `core-design`(token/组件/护栏)与 `core-directory`/`feature-im`(人员选择、分享入口);WebView tab 保留为「降级/兜底」入口 |

## 一、现状盘点

### 1.1 云文档(we-meet-docs)是什么

docs = [suitenumerique/docs](https://github.com/suitenumerique/docs) 的分支(镜像名 `app-impress` 5.4.1),三件套独立部署:

- **后端**(`src/backend`,Django 5 + DRF):文档树(`treebeard` MP_Node,`path` + `steplen=7` 的 base62 手册排序)、软删/恢复(回收站)、收藏、链接分享(`link_reach`/`link_role`,与祖先合成 `computed_link_reach/role`)、访问控制(`DocumentAccess` 按 path 前缀继承;角色 reader/commenter/editor/administrator/owner)、邀请(邮箱邀请,首次登录转 access)、评论/线程/表情、`abilities` 细粒度权限字典。
- **内容存储**:S3(OSS),key 为 `{doc_id}/file`,内容为 **base64 文本,解码后是 Yjs 二进制更新**(不是 JSON!);历史版本 = S3 对象版本(`versions/` 端点直接透传)。无独立 Version 模型,恢复版本由 Web 取历史内容、写存储并对协作 Y.Doc 执行 `revertUpdate`；单独 PATCH 不构成完整恢复。
- **协同服务**(`src/frontend/servers/y-provider`):单进程 Express + **Hocuspocus**,WS 路由 `GET /collaboration/ws/?room=<doc-uuid>`(房间名 = 文档 UUID);`onConnect` 转发请求到后端 `GET /documents/{id}/` 拿 `abilities`,据此设 `connectionConfig.readOnly`;从 `Cookie: docs_sessionid` 取 sessionKey。**Updates 只在内存**,持久化靠前端每 60s / 离开页 `PATCH /documents/{id}/content/`(base64 Yjs 更新)。另有 `/api/convert/`(markdown / Yjs / BlockNote JSON ⇄ 互通)。
- **前端**(`src/frontend/apps/impress`):Next.js 16(Pages Router,静态导出)+ **BlockNote 0.51**(TipTap/ProseMirror 之上的块编辑器)+ `@hocuspocus/provider` + Yjs;评论锚定在 Yjs 文档内的「comment mark(threadId)」,DB 只存 body/metadata;离线:service worker(workbox)+ idb + 乐观保存。
- **we-meet fork 的改动**(已上线,与 App 强相关):`users/session-ticket/`(s2s 单据)+ `session-from-ticket/`(一次性票据换 docs 会话,60s 有效、用一次即废,见 `core/api/session_bootstrap.py`);`search-for-user/list-for-user/grant-access-for-users`(s2s,按 `sub` 定位用户);`formatted-content`(上游已有,保留);内嵌收敛(UA 标记 `WeMeetApp`、`?embed=1`、`?chrome=none`、`wemeet-*` 消息协议、主题/语言跟随);CSP `frame-ancestors` 白名单;zh-CN 语言与国内 OSS 兼容。

### 1.2 App 端立项时基线(2026-09-06，非当前完成状态)

- 纯原生 Kotlin + Compose + Material 3,6 个底部 tab:消息 / 日历 / 会议 / 通讯录 / **云文档** / 任务(`MainTabScreen.kt` 的 `MainTab` 枚举)。多模块:`app` + `core-design`(token/组件/护栏)+ `core-directory` + `feature-im` + `feature-assistant`;Retrofit 2.11 + Moshi + OkHttp 4.12、Compose BOM 2024.10、AGP 8.7.3 / Kotlin 2.0.21;**无 DI 框架**——`WeMeetApp` 手工装配,AFeature 模块经 `Deps` 接口注入(`ImDeps/AssistantDeps/DirectoryDeps/CallHost`),ViewModel 用 `Provider.Factory`;**无 Room/DataStore**——持久化 = EncryptedSharedPreferences(token)+ SharedPreferences + JSON 文件(`HistoryStore`)+ 内存 StateFlow(`UserDirectory` 1h TTL 一类);Getui 推送、PostHog、**minSdk 29 / targetSdk 34**(`app/build.gradle.kts`,README/CLAUDE.md 的 24 已过时)。
- 云文档相关代码体量:WebView 集成约 **1400 行**(`ui/docs/DocsScreen.kt` 565 + `DocsViewerScreen.kt` 96 + 登录 WebLoginScreen 306 + MainTab 集成 ~90 + AppNav ~25 + 会话/搜索 API 82 + IM 侧 doc-card/选择器 ~320),其中加载/桥接/会话引导约 780 行 —— 原生化的**回收面**与**替换成本**都以此为基数。
- 「云文档」= **常驻 WebView**(实例在 `MainTabScreen` 层持有、预加载)+ 独立 `DocsViewerScreen` 深链阅读 WebView(`chrome=none` 阅读态)。已实现并上线:
  - 登录:WebView 内 Keycloak OIDC(PKCE)登录,进程级 CookieManager 共享 KC 会话 cookie → docs tab 免登;另有 `POST /api/v1.0/docs/session/` 票据兜底(`DocsApi.createSession`),不依赖 KC 会话。
  - 嵌入协议:UA 标记 + 主题/语言跟随 + `DocsWebViewClient`(拦截导航、面板状态)+ `DocsHostBridge`(`WeMeetHost.postEvent`:分享到聊天、全局搜索、`wemeet-embed-hello/host-hello` 能力握手)+ 分享文档到聊天(DocPickerDialog/DocCardBubble)。
  - 全局搜索已接入 docs 代理(`SearchApi.searchDocs` → meet `GET /api/v1.0/docs/search/`)。
- **现状痛点**(用户视角):
  1. **风格割裂**:docs tab 是 Web 站点 Chrome(悬浮面板、Web 列表项、Web 弹窗/抽屉、Web loading),与其它 5 个原生 tab 不是一套语言;
  2. **交互割裂**:返回键层级、长按、下拉刷新、多选、手势、暗色模式下的加载/空态都与原生不一致;Web 交互在手机上偏桌面(行内菜单、hover 态);
  3. **体验问题**(p3-docs-app.md 记录的):KC SSO 会话 10h/30min 过期 → 隔天首开要输一次 OTP;language/theme 三仓(meet/docs/App)强耦合,靠 UA/桥同步;WebView 加载慢、内存大、无法离线;
  4. **维护成本**:双 UA 标记、桥协议版本、docs 镜像收敛逻辑都散在「App ↔ docs 镜像」两处,需三端同步发版。

### 1.3 不做的范围(本评估)

电子表格(Sheets)、多维表格(路线图已明确不做)、模板、AI 助手/工具栏(BlockNote AI、`ai-proxy` 等)、PDF/DOCX/ODT 导出、房间内文档侧栏、按事件建文档模板。这些维持 WebView/Web 现状。

## 二、可行性评估(分层)

### 2.1 数据面:接口就绪度(结论:高)

docs 的 REST 面完整,除以 `session cookie + CSRF` 为认证外没有障碍:

**认证三通道**

| 通道 | 用途 | App 可用性 |
|---|---|---|
| `SessionAuthentication`(session cookie `docs_sessionid` + `X-CSRFToken`) | 全部用户 API(documents CRUD/children/tree/versions/favorite/link/trashbin、accesses、invitations、threads/comments、ask-for-access、users/me、search、attachment-upload、media-check、formatted-content) | **✅ 可用**。引导链路已存在:App 用自己的 Bearer 调 `POST /api/v1.0/docs/session/` 拿带上票据的 URL → 原生 OkHttp 直接 GET `session-from-ticket/?ticket=…`(带 CookieJar,跟随 302)→ 拿到 `docs_sessionid` + `csrftoken` → 后续请求带 cookie + `X-CSRFToken`(写操作)。Django 会话 12h(`SESSION_COOKIE_AGE`),可静默续期 |
| `ServerToServerAuthentication`(meet 后端持静态 Bearer) | s2s 端点:`users/session-ticket/`、`create-for-owner`、`search-for-user`、`list-for-user`、`grant-access-for-users` | ✅ 已由 meet 后端代理(不走 App 直连) |
| `external_api`(`/external_api/v1.0/`,加密 JWE) | 服务账号级 documents/users | ⚠️ 不适用:它是 s2s 通道,身份不是用户,App 不应持有 |

**关键事实(fact 清单)**

| 能力 | 端点/机制 | 原生可行性 |
|---|---|---|
| 文档列表/筛选/排序/分页 | `GET documents/?is_creator_me=&is_favorite=&q=&title=&ordering=&page=(≤200)` | ✅ 列表返回 `abilities/user_role/is_favorite/excerpt/updated_at/numchild/depth/creator…` 足够列表 UI |
| 文档树(懒加载) | `GET documents/{id}/children/?page=`、`GET documents/{id}/tree/` | ✅ 左栏树可原生(懒加载分页) |
| 文档详情 | `GET documents/{id}/`(含写 LinkTrace) | ✅ |
| **阅读正文** | `GET documents/{id}/formatted-content/?content_format=json\|markdown\|html`(y-provider 服务端转换) | ✅ **这是本方案的最大支点**:`json` = BlockNote JSON(结构化、保样式),`markdown/html` 为保底。⚠️ 依赖 y-provider 服务可用(部署监控点) |
| 图片/附件 | `attachment-upload/`(multipart)+ `media-check/` + `MEDIA_BASE_URL/media/{pk}/attachments/…`(nginx media-auth 子请求,需 docs 会话 cookie) | ✅ OkHttp/Coil 带 cookie 直取;上传走 multipart |
| 搜索 | `documents/search/?q=`(La Suite Find 索引器,未配置回退标题 ILIKE) + meet 代理 `api/v1.0/docs/search/` | ✅ 原生搜索页;全局搜索继续用 meet 代理 |
| 收藏/移动/复制/重命名/删除/恢复 | `favorite/`、`move/`、`duplicate/`、`PATCH documents/{id}/`、`DELETE`、`restore/`、`trashbin/` | ✅ |
| 分享(链接权限/成员/邀请/申请访问/离开) | `link-configuration/`、`accesses/`、`invitations/`、`ask-for-access/`、`leave/`、`users/?q=` | ✅ |
| 评论/线程/表情 | `threads/`、`comments/`、`reactions/` | ✅ 列表/发表/回复/解决/表情全 REST。⚠️ **内容锚定(高亮定位)在 Yjs comment mark 里**,原生侧只能显示「评论列表 + 引用文本摘要」;点击定位 → 跳编辑画布(WebView) |
| 版本(列表/查看/恢复) | `GET documents/{id}/versions/`、`versions/{vid}/` | 原生分页列表；查看和恢复交由 Web 版本弹窗。Web 恢复除了 PATCH，还调用 `revertUpdate(provider.document, …)` 同步协作房间，原生不得只回写旧 base64。 |
| **实时协同** | `GET /collaboration/ws/?room={uuid}`(Hocuspocus,y-websocket 二进制协议;`docs_sessionid` cookie 鉴权;服务端按 abilities 定 readOnly) | ⚠️ 协议可对接,但客户端需要 **Yjs 实现** —— 见 2.2 |
| 新建文档 | `POST documents/`(可带 `file` 走转换导入;空白文档无需 content) | ✅ 原生「新建」= 建空文档 → 跳编辑画布填充 |

### 2.2 编辑面：当前不自研原生协作编辑器

结论基于本项目已有实现和验证成本，不依赖“生态中绝对不存在可用库”的判断。原生编辑至少需要验证 BlockNote 块结构与行内语义、Yjs 更新与撤销、Hocuspocus 同步和重连、评论锚点、历史恢复与 Web 互操作。

阅读器只能复用部分展示组件，不能自然演进成兼容的协作编辑器。当前路线不包含“单人轻改后整文档 PATCH”，也不把全原生编辑列为必然的远期目标。只有出现 Web 方案无法满足的明确产品需求，才另立技术验证项目；相关生态选型在该项目启动时重新核实。

### 2.3 界面面:可行性(结论:高)

- 全部列表/详情/弹层/抽屉模式在 App 现有模块都有范式(`feature-im` 的会话列表/详情/更多菜单、`ui/tasks` 的任务列表/编辑、`ui/calendar` 的层级选择、`core-directory` 的人员选择器);
- 设计系统与护栏完备(`设计规范.md` + `checkDesignTokens` 10 条规则);
- 阅读态渲染器:BlockNote JSON → Compose 是一个**确定性的节点映射**(约 20–25 种块 + 行内标记),中等难度、可单测、可快照测试;特殊块(PDF/视频/多列)降级为「卡片 + 用网页版查看」。

## 三、方案对比

| 方案 | 收益 | 主要成本与风险 | 决策 |
|---|---|---|---|
| 全原生编辑 | 可深度控制输入与平台交互 | 协作数据兼容、块模型、重连与恢复需自研验证 | 不纳入当前路线 |
| 原生管理/快照阅读 + Web 编辑器 | 复用 App 导航与交互，同时保留现有编辑能力 | 保存边界、生命周期、跨端权限与版本兼容仍是高风险集成点 | 继续采用，按第五节验收 |
| 完整 Web 页面 | 功能覆盖随 Web 演进，维护面较小 | 手机交互、启动和平台集成仍需优化 | 保留为功能回退；不宣称可规避断网、服务故障或宿主销毁丢数据 |

### 4.1 架构总览

```
      │   ├── dto/   DocumentDto · AbilitiesDto · ThreadDto · VersionDto …

      宿主通过 DocsDeps 回调提供导航、人员选择和分享到聊天；feature-docs 不反向依赖 app，也不直接耦合 feature-im 内部 data API
```

设计参数:沿用 `feature-im` 的「data/domain(如有)/ui + Repository + StateFlow<UiState> + LazyColumn + 三态成组」范式;模块边界同样走 **`DocsDeps` 接口注入**(宿主 `WeMeetApp`/`MainTabScreen` 实现:提供 `shareToChat(doc)`——复用 `feature-im` 的 `ForwardPicker`、`pickUser(s)`——复用 `core-directory` 的 `ContactPicker`、`openDoc(url)` 深链放行、`languages` 取应用语言);持久化沿用现有模式(SharedPreferences/JSON 文件 + TTL,不引入 Room/DataStore);不做新 DI 框架;模块内所有用户可见文案进 `strings.xml`(5 语言键数对齐:values/values-zh-rCN/values-de/values-fr/values-nl,中英必齐)。

### 4.2 认证与会话(核心新部件:`DocsSessionManager`)

两个独立 Cookie 栈并存；它们仍共享当前 App 身份，必须统一管理账号切换和失效时序，不能把物理隔离等同于账号隔离：

| 栈 | 使用者 | 引导 |
|---|---|---|
| WebView 栈(现状) | 深链兜底 / 特殊块降级 / 编辑画布 | `Bearer → POST /api/v1.0/docs/session/ → ticket URL`(或 KC SSO) |
| **原生栈(新)** | 全部原生 REST + 媒体 + (远期)协作 WS | `Bearer → POST /api/v1.0/docs/session/` 拿票据 URL → OkHttp(CookieJar)GET `session-from-ticket/?ticket=…` 跟随 302 → cookie:`docs_sessionid`(+`csrftoken` 由后续响应 Set-Cookie/第一次 GET 获得) |

**会话生命周期**:
1. 冷启动/首次进入 docs tab:静默建会话(`DocsSessionManager.bootstrap()`,单飞；目标需有端到端超时，当前 connect/read/write 超时不等于整个引导链限时);
2. 401，以及明确表示未认证或 CSRF 失败的 403，单飞重建会话、最多重试一次；普通 403 保留权限错误语义。Django SessionAuthentication 未登录也可能返回 403，不能一概解释为文档无权限。
3. Django 会话 12h 有效;App 长登录期间每次会话过期自动重建(体验优于现状:现状 KC SSO 30min idle / 10h max 后会看到登录页);
4. 登出(App 级)与 WebView 栈的 cookie 清理保持一致(`signOut` 现有逻辑延长到原生栈 CookieJar);
5. 写操作:同源网络请求附带 `X-CSRFToken` 与 docs 的 Origin/Referer；HTTPS Django CSRF 校验不仅比较 token。Cookie 必须合并增量 Set-Cookie、处理删除与有效期，并限定协议、主机、端口与路径。不同来源不能污染凭据存储。票据 URL 不进入 HTTP 日志。
6. **存储**:原生栈的 `docs_sessionid`/`csrftoken` 存 **EncryptedSharedPreferences**(独立会话存储),不落明文。

**不新增票据接口**：现有 URL 可以直接发起引导；返回 ticket 明文并不能省去换取 docs Cookie 的请求。引导成功必须检查实际取得 session，不能只检查最后的 HTTP 200。

### 4.3 数据层(API 映射)

| 原生屏/动作 | 端点 | 备注 |
|---|---|---|
| 主页「全部」 | `GET documents/?ordering=-updated_at`(分页 20/页,page_size≤200) | 原生分页 + 增量加载;`abilities` 决定行内操作可用性 |
| 「我的」/「收藏」 | `?is_creator_me=true` / `?is_favorite=true` | 主页筛选条;默认排序即「最近」 |
| 回收站 | `GET documents/trashbin/` | 恢复 `restore/`;彻底删除按 `abilities` 开放 |
| 树(左栏/移动选择器) | `children/` 懒加载分页 + `tree/` 祖先链;提交 `move/` | 移动:懒加载树弹层 + 当前节点禁用 |
| 详情头 | `GET documents/{id}/` | title/作者/时间/状态;**emoji 图标 = 标题首字符 emoji 的解析**(与 docs 前端 `getEmojiAndTitle()/updateDocEmoji()` 同语义:emoji 存于 title 字符串,修改即 PATCH `title`),原生侧实现等价解析函数 |
| 阅读正文 | `GET documents/{id}/formatted-content/?content_format=json` | 当前接口没有已验证的 ETag/304 契约。前台请求保存快照，解析异常显示 Web 降级入口；Markdown 也依赖同一转换服务，不作为服务不可用时的可靠降级。 |
| 评论 | `GET/POST documents/{id}/threads/`、`/threads/{tid}/comments/`、`reactions/`、resolve | 列表/发表/回复/表情/解决全原生;正文锚定高亮跳编辑画布 |
| 版本 | `GET versions/` + 恢复;查看旧版本 | 查看 → WebView(或远期 yrs 解码) |
| 分享 | 链接权限 `PUT link-configuration/`;成员 `accesses/` CRUD;邀请 `invitations/`;申请 `ask-for-access/`;离开 `leave/` | 成员 accesses 返回无分页数组，邀请 invitations 返回分页对象；本地设置显示 `link_reach/link_role`；有效继承状态用 computed 字段说明，可选项只取 `abilities.link_select_options`。管理、查看和离开各按独立 abilities 控制，不由角色或 retrieve 推测。 |
| 搜索(模块内) | `GET documents/search/?q=` | 与全局搜索(meet 代理)同口径 |

| 新建 | `POST documents/`(title,空内容)→ 跳编辑画布 | |
| 导入 | `POST documents/`(multipart `file`)+ 上传后跳编辑画布 | 列表入口「导入」(docx/txt/md 等,受 `CONVERSION_*` 配置限制) |

**错误语义**:
- docs 认证失败重建一次，仍失败显示 docs 会话不可用与重试入口；只有宿主认证层确认 App 凭证失效才全局退出。普通 403 表示无权限；404 表示不可用且可能隐藏存在性，不擅自展示申请入口；超时/5xx 不清空已有正文。不得假设错误响应包含 abilities。
- `429` → 列表节流`180/hour`(users 搜索专有)与 docs 节流按配置;出现时静默退避 + Toast。

### 4.5 阅读态渲染器(`BlockNoteJsonRenderer`)

**输入**:`formatted-content?content_format=json`(BlockNote JSON 块数组)。**输出**:Compose 递归渲染。

- 块映射目标（按真实样例验收，未支持的格式显式降级，不能“见过就算支持”）:paragraph / heading(level1-6)/ bulletList / numberedList / todoList(taskItem + 勾选框)/ quote / codeBlock(带语言标签 + 单行等宽字体 + 复制按钮)/ table(表头、行列合并、单元格对齐与背景色,用 Compose Canvas 或嵌套 Row/Column;复杂表格降级「截断 + 打开 Web」)/ image(Coil + 点击全屏 Lightbox,参考 `feature-im` ImageLightbox)/ video / file(附件卡片,点击预览/下载,同 `feature-im` 附件样式)/ callout(图标 + 左色条)/ multiColumn(按列数渲染,窄屏单列叠加 + 提示)/ pdf(降级卡片)/ uploadedFile、linkToDoc(卡片:图标 + 标题 + 打开)→ 路径链接(interlinking,点击跳原生详情)/ divider / pageBreak(提示)/ 行内:bold/italic/underline/strike/code/highlight/link/mention(@渲染为 Chip 样式,点击查人员卡)/ comment mark(渲染为浅底高亮 + 点击进评论线程)/ emoji。
- **样式策略**:沿用 `design` 与 docs 的「编辑器内容风格」一致性 —— 正文 bodyLarge、标题按 level 取 type scale(`headlineSmall/titleLarge/titleMedium`…),引用/代码/表格用 container 色 + `onSurfaceVariant`;**所有取色走 token**(新增「文档内容」语义色进 `WeMeetExtras.docs.*`),表格/代码块背景属「文档内容样式」——护栏若误报,使用 `// design-exempt: 文档内容区按编辑器语义样式`(与现有 `docs/设计规范.md` 的豁免先例同格式,需在 PR 说明)。
- **降级规则**(渲染器永远不崩):未知块/未知 mark → 渲染为一个「块占位卡片」+ 文案「该内容暂不支持在客户端预览」+「用网页版打开」按钮(跳阅读态 WebView);图片加载失败 → 占位 + 重试;文档过长 → 视口内分块 + 懒加载图片,避免超长 LazyColumn 崩。
- **空文档态**:空白正文 → 「这是一篇空文档,点击开始编辑」的引导空态(与 docs Web 一致)。
- 性能:文档 JSON 可能数百 KB;解析在 IO/后台(协程 + 结构复用),渲染用 LazyColumn(块级)+ 记忆化;大图 Coil 缩放。

### 4.6 编辑画布(WebView 单页:`DocEditorCanvas`)

**形态**:详情页内「阅读态 ↔ 编辑态」切换(用编辑按钮/点击正文进入;顶部保持原生 `WeMeetTopBar`,工具栏/浮层属 docs 编辑器)。编辑态 = 一个**独立轻量 WebView**(复用 `createDocsWebView` 全套配置:MATCH_PARENT、UA 标记含 `theme=`,允许域拦截、`WebViewClient` 先于 `loadUrl`、`deferInitialLoad`),直载:`https://docs…/docs/<docId>/?embed=1&chrome=editor&lang=<app语言>`(进站走票据 URL,复用 `loadDocsTabEntry`/`docsEntryUrl` 既有逻辑;主题走 UA 标记,与 tab WebView 同机制)。

**docs 前端集成边界**:`?chrome=editor` 收敛:隐藏 docs 站点级导航、列表和用户区，保留编辑标题、评论侧栏与编辑所需浮层,只保留 **BlockNoteEditor + 其原生工具栏浮层 + Comments 浮层/ThreadsSidebar**(在编辑器内) —— 即「无站点壳的纯编辑器」;编辑器外的路由(如 AI、导出、分享弹窗)入口全部交给宿主(已有 `sendToHost` 通道,**扩展必须走新增 message type**——`DocsHostBridge` 约定只保留一个 `WeMeetHost.postEvent(String)` 方法,新命令一律加 type,未知 type 静默忽略,老 App 与老镜像互不破坏)。

**已实现桥接与入口契约（2026-09-07）**:
- docs → 宿主：`wemeet-editor-dirty {docId, dirty}`、`wemeet-save-result {docId, requestId, success}`。
- 宿主 → docs：`wemeet-save-now {docId, requestId}`。失败不退出，旧镜像不支持确认时不能宣称保存退出安全。
- 评论与版本入口通过 URL `thread` / `version` 参数，由 Web 等数据就绪后消费。AI、导出和文档工具箱保留 Web 入口；不预先声明尚未实现的 ready/edit-mode/export/AI 消息。

**宿主(App)职责**:
- 编辑态的标题/emoji 使用 Web 自身标题组件，避免原生 PATCH 与 Web 标题状态同时写入。原生详情仍提供重命名；退出画布后刷新元数据和正文。
- 返回目标：先关闭键盘/可关闭的 Web 浮层，再请求退出。当前只完成正文 dirty 与保存响应守卫，浮层优先级尚待实现。退出选项为继续编辑/保存并退出；不提供“放弃修改”，因为协作更新可能已传播给他人，销毁页面不能撤销它们。60s 定时与 beforeunload 不能作为可靠退出保证；完整状态机见 §4.12。
- 主题/语言/深色:复用现有桥(`embedderTheme/embedderLanguage` 已工作);
- 正文编辑入口按 `abilities.can_edit`；有相应权限的评论定位和历史版本预览仍可进入 Web，不等同于授权编辑。
- 评论锚定：使用 URL `thread=<id>`，等编辑器及线程加载后调用 CommentsExtension.selectThread；页面加载完成并不代表编辑器可消费消息，不再依赖一次性注入。
- 内存:画布 WebView 只在编辑态创建、退出销毁(与常驻 tab WebView 互不干扰的真实隔离);**常驻 tab WebView 在新版原生主页就绪后即可退役**(见 4.9),App 里只保留「深链兜底/特殊块兜底」的轻量 WebView(`DocsViewerScreen` 体系)。

### 4.7 跨端协同(PC Web ↔ Android 原生)——本设计的第一等公民

docs Web 端(PC 浏览器)与 Android 原生端操作的是**同一个 docs 实例**(同一 Django/PG/S3、同一 Keycloak realm、同一 Hocuspocus 房间),共享数据源，但 REST 快照、编辑器内存、客户端缓存和权限观察时间不同；**必须验证「端到端切换」的每一个入口**。PC 端分享的东西,Android 必须能无缝打开,反之亦然。

#### 4.7.1 身份与数据连续性（共同数据源，不等于已验收）

| 依据 | 事实 |
|---|---|
| 同一用户 | PC 浏览器走 Keycloak SSO(`docs` client);Android 原生栈走「App Bearer → meet `docs/session/` 票据 → docs `session-from-ticket`」——二者最终都解析到**同一 `sub` 对应的 docs User**(`session_bootstrap._resolve_user` 按 sub/email 认人并懒建) |
| 同一文档树/同一份数据 | 列表/筛选/详情/tree 全部 docs REST、按登录用户可见性过滤 —— 响应仍需正确解析、分页和刷新；共享数据库不保证当前屏幕一致 |
| 邀请转正 | PC 邮箱邀请 → 受邀用户在 Android 登录同一账号那一刻,Invitation 自动转 DocumentAccess(`User.save` 首次登录钩子)。既有用户、邮箱匹配、邀请转正时机和列表刷新必须分别验收，不能仅凭同账号作可见性保证 |
| 权限变更由服务端裁决 | 权限/链接权限/移动/删除都在 docs 后端裁决;Android 每次拉取都是后端现算(`abilities` 随响应下发,缓存仅作离线壳、非权威态) |

#### 4.7.2 跨端打开矩阵(PC → Android)

| PC 端的动作 | Android 端发生什么 | 打开路径 |
|---|---|---|
| Web(meet 框架内)docs「分享到聊天」 | IM 收到 doc-card 消息(带 docId+title+url) | **IM 卡片点击 → 原生 `DocDetailScreen`**;docId 直接取自卡片字段(不再依赖解析 URL),url 仅作 WebView 兜底 |
| docs 里复制链接(任意 reach)发给别人 / 发进聊天正文 | 聊天文本链接 / 深链 | 链接解析器(`docs.we-meet.online/docs/<uuid>` 等)→ 原生详情;**无权限 → ask-for-access 原生流**;无法解析 → 浏览器/WebView |
| 全局搜索(meet Web 或 App)命中文档 | 搜索结果点开 | 原生详情(`SearchApi.url` 解析 docId,兜底 WebView) |
| 会议纪要自动落 Doc(`create-for-owner` 已有)后在 IM 推送链接 | 会议历史/IM 内 doc 链接 | 原生详情 |
| 邮箱邀请 | 受邀用户在 Android 登录后 | 文档已在列表(4.7.1),刷新可见 |
| PC 批准了某人的 ask-for-access | Android 请求者 | 列表/详情刷新后恢复可见;详情页停在「申请访问」态 → banner 提示重试 |
| PC 端编辑(实时) | Android 阅读/编辑同一文档 | 4.7.4 的新鲜度与协同策略 |
| PC 调整链接权限/成员/移动/删除 | Android | 每次拉取后端现算,无本地权威态 |

#### 4.7.3 反向(Android → PC)

| Android 的动作 | PC 端发生什么 |
|---|---|
| 原生「分享到聊天」 | 与 Web 同一条 doc-card 链路(grantDocAccess + 卡片格式均已存在),PC 聊天显示同一卡片 |

#### 4.7.4 实时协同与新鲜度(PC 在写、Android 在看/在改)

1. **阅读态新鲜度**(PC 编辑者持续改,Android 阅读者必须能看到):
   - 进入详情与切回前台(`ON_RESUME`)立即重取元数据、权限和 `formatted-content`；后台停止轮询，显式刷新与轮询不得并发覆盖。
   - 前台每 30s 拉取持久化快照，有变化才重渲染。接口需要读取存储并转换内容，不能称为零成本。Web 当前通常每 60s 持久化，原生读者可见延迟约为持久化间隔 + 轮询间隔 + 请求耗时；不是实时协作阅读。
   - 轮询发现变化 → 顶部轻提示「内容已更新」+ 自动重渲染(渲染器为纯函数,重建成本低)。
2. **编辑态协同**(Android 画布 = 与 PC Web 同一个 Hocuspocus room):
   - 画布复用 docs 编辑器；在双方已鉴权、连接并同步同一房间后，验收光标、正文和评论锚点互见，断线与失权不能沿用在线假设；
   - `?chrome=editor` 复用 Hocuspocus 连接和编辑器，但保存确认、WebView 生命周期、权限变化和断线重连仍有集成与回归成本。
3. **离线/冲突保护**(防 Android 写覆盖 PC 的实时编辑):
   - 原生层不提供正文 PATCH 或版本回写；版本恢复同样通过连接协作房间的 Web 实现。`COLLABORATION_WS_NOT_CONNECTED_READ_ONLY` 是协作保护的一部分，不能代替 CRDT 同步，也不作为开放原生写入的条件。
   - 保存退出必须携带 `docId/requestId`，收到匹配的 `wemeet-save-result(success=true)` 才销毁 WebView；失败、离线、超时保留页面与脏状态。保存中的新增编辑必须再次落库；远端事务不能清除本地未保存标记。
   - Android 画布遵循 docs 自身保存队列(60s + 离页),**不在 App 侧另做 PATCH**,不引入第二套写路径。
4. **阅读→编辑切换**:进入编辑态前,画布按 docs 现有行为先拉最新 content 并 `applyUpdate`,无需 App 介入。

#### 4.7.5 外部系统链接(可选增强,不做强依赖)

- 手机系统里点击 `https://docs.we-meet.online/docs/<uuid>`(微信/Safari 等)→ 浏览器打开 docs Web —— **本身是正常路径**(docs Web 手机可用、同 realm SSO);
- 可选增强:给 App 加 `docs.<domain>` 的 `intent-filter`(+ `assetlinks.json` 验证),系统直接唤起 App 进原生详情;主场景不依赖它,列 M-later。

### 4.8 离线与缓存

- 当前原生列表和正文仅保留进程内状态，不能声明离线可用。已有内容遇普通网络失败保持显示；权限撤销或文档不存在时清除详情数据。
- 持久化离线阅读单独安排：需账号隔离、退出清理、容量限制、更新时间提示及权限失效规则。ETag/304 需先设计并测试后端契约，不能作为已有能力验收。
- 写操作离线队列(本轮不做):新建/重命名/收藏等离线为「失败提示」+ 已存在错误语义;Web 离线编辑能力需单独在 Android WebView 验证，不由桌面 service worker 行为推断；未验收前不承诺退出/进程被杀后可恢复;
- 回收站、版本、评论:仅在线(有缓存不承诺)。

### 4.9 兼容与回退（目标待实现）

- 现有源码未找到 `BuildConfig.DOCS_NATIVE_ENABLED`。构建开关也不能替代已安装 App 的运行时回退能力，不能写成已具备的灰度手段。
- 使用能力握手判定保存确认、评论定位和指定版本是否可用（§4.12）；UA 或 `chrome=editor` 只表示嵌入形态。忽略未知消息解决的是解析兼容，不保证新 App + 旧前端安全。
- 打开文档之前，按能力选择原生管理/阅读 + 编辑画布或完整 Web 入口；已经有未保存内容时禁止自动重载、换宿主或销毁来回退。回退目标自身也须验证退出保存。
- 发布组合必须覆盖新旧 App × 新旧前端、旧资源缓存与前端回滚。新 App 未具备运行时兼容分支前，只允许使用固定已验证的组合进行测试。
- 当前复用 meet 的票据 API，不增加 ticket 明文字段。后续能力或错误码扩展另列服务端契约变更，不能继续统称“主路径零改动”。

### 4.10 安全

- 原生栈保存 `docs_sessionid`/`csrftoken` 于 EncryptedSharedPreferences(独立会话存储),不落明文;
- 会话引导的最小化:票据一次性 60s,OkHttp 跟随 302 不转发 Cookie 到非 docs host(拦截器校验 host,参考 `DocsWebViewClient` 的允许域清单);
- 读 `config/`(AllowAny)不携带会话;媒体请求仅 `MEDIA_BASE_URL`。

#### 4.11.2 新增样式 token 与扩展点(`core-design` 的规范动作)

**原则:优先复用 `core-design` 现有 token,只有「语义确实需要」才新增;新增一律走规定的四处扩展点,禁止在调用处 `if (isSystemInDarkTheme())`。**

| 用途 | 策略 |
|---|---|
| 正文/标题/弱化文字 | `MaterialTheme.colorScheme.onSurface` / `onSurfaceVariant`;标题按 level 映射 M3 15 档(headlineSmall/titleLarge/titleMedium…),**不新增字号** |
| 链接 / 互链卡片 | `colorScheme.primary`(+ `onSurfaceVariant`),不新增 |
| 引用块 / callout / 代码块 / 表格容器 | **先试 M3 面色** `surfaceContainerLow/High/Highest` + `onSurface`/`onSurfaceVariant`(成对面色,对比度由 M3 保证);视觉区分不足再补**一对** `docs.emphasisContainer/onEmphasisContainer` |
| 评论锚定高亮 | 新增**一对** `docs.commentHighlight` / `docs.commentHighlightText`(唯一确定的新语义色) |
| 代码/表格边界线 | `colorScheme.outlineVariant`(结构线,非文字),不足 3:1 再补 `docs.divider` 一档 |

**新增色的规范动作(唯一路径)**:
1. `core-design/…/ui/theme/Color.kt` 加 `Light…`/`Dark…` 成对字面量(注释写明对比度计算值:文字 vs 底 ≥4.5:1、容器 vs 页面 surface ≥3:1);
2. `Theme.kt` 加 `data class DocsColors(...)` → `WeMeetExtras` 增 `docs: DocsColors` 字段 → `LightExtras`/`DarkExtras` 两处接线;
3. 对比度写进 `core-design` 的 `ColorContrastTest` / `FoundationTokensTest` 同款单测(先例:通话红绿、日历 reminder 的踩坑记录都在 Color.kt 注释里);
4. 消费侧一律 `WeMeetTheme.extras.docs.*`,不出现色值字面量(`raw-color`/`raw-color-named` 护栏自动覆盖)。

**无需新增**:字号(15 档 + LabelTiny/CodeDisplay 已有)、间距(`Dimens` 8dp 网格 + 文档块间距豁免)、Shape/Elevation(`JusiShapes`/`Dimens.Elevation*`)、图标(`material-icons-extended`,feature-docs 自行声明依赖,不改变 core-design 的 api 面)。

**共享组件边界(遵守 core-design 的定位)**:core-design 只放「所有 UI 都可能用到」的东西(其 build.gradle.kts 注释明示),所以:
- 直接用:`WeMeetTopBar`、`WeMeetLoading`/`WeMeetInlineLoading`、`WeMeetEmptyState`/`WeMeetInlineEmptyState`、`WeMeetErrorState`/`WeMeetInlineErrorState`、`PrimaryButton`/`SecondaryButton`/`DangerButton`、`DestructiveConfirmDialog`;
- 业务组件留 `feature-docs`:`DocListItem`(文档列表行)、`DocTypeIcon`、`DocCardActionsSheet`、`CommentBubble`、`VersionRow`、`DocReader`(渲染器)——遵循同套 token 与组件范式(先例:`feature-im` 的会话行/群头像不进 core-design);
- 跨模块复用:`core-directory` 的 `MemberAvatar`/`ContactPicker`、`feature-im` 的 `ForwardPicker`/`ImageLightbox` 参考(经 `DocsDeps` 注入,不跨模块直接 import);若未来日历/任务也要「文档卡片」,再评估提入 core-design/core-directory。

### 4.12 第二轮补充：发布前必须补齐的状态与契约（实施中）

本节保留第二轮目标设计，不能计入第一轮已完成清单。2026-09-07 开始实施：v2 握手、整体保存协调、账号代次隔离、可见性/网络控制的刷新、原生评论草稿和受限链接配置已落实到代码。实际验收与剩余项目见《云文档原生化_复审与功能对齐》的第三轮实施记录；不是整份设备/权限矩阵已经通过。

实现采用 `WAITING / READY / SAVING / FAILED / UNSUPPORTED / CLOSED`。不再用 clean/dirty 决定能否直接退出：READY 只说明保存协议就绪，每次退出仍请求整体保存。HTML 加载完成后握手等待 30 秒；进入 UNSUPPORTED 后展示重试提示，继续低频握手，同一实例迟到的有效 ready 可恢复到 READY。HTML 完成不代表异步编辑器已加载，超时不能据此判定协议不兼容。手动重试从原始编辑 URL 重新换票进站，生成新实例身份，拒绝旧页面回执。Web 保存等待 12 秒，App 等待 15 秒；旧前端在握手前不能接收输入。

**A. 能力握手与退出状态**

- 沿用单个 `postEvent(String)` 和现有 hello 通道扩展可选能力，目标包含 `protocolVersion`、`saveConfirmation`、`commentNavigation`、`versionPreview`；具体字段在实现时固定契约。协议就绪需同时验证来源、当前 docId 与本次页面加载身份，不能仅检查主框架 host 或 UA。
- 状态至少为 `unknown / clean / dirty / saving / failed`。初始 unknown；文档数据和保存协调器就绪后才允许 clean。握手超时表示能力未知，不表示已保存。旧前端只能进入已验证的兼容路径，不能盲目关闭编辑画布。
- 每次载入生成 `editorInstanceId`，请求携带 docId、instanceId、requestId；响应三者均匹配才消费。导航/重载换代，旧响应作废；重复请求须幂等回复，超时重试不把上一轮成功混入本轮。
- 关闭时先阻止新增输入并提交正在组合的输入法文本，再在 Web 内执行最终 flush；待全部任务完成后回应成功并销毁。单纯“等 dirty=false”仍可能与最后一次输入竞态。失败恢复编辑能力并保留错误与草稿；用户继续编辑后需重新计算保存状态。

**B. 保存确认的范围**

| 数据 | 持有者与退出要求 |
|---|---|
| 正文/Yjs | Web；已送达协作房间不等于已持久化，成功必须覆盖关闭时的本地版本；不另起原生 PATCH |
| 标题/emoji | Web 标题组件；失焦提交与在途 mutation 必须完成，正文成功不能代替标题成功 |
| 图片/附件 | Web 上传流程；上传、检查与引用写入均完成才可宣称全部保存；失败给继续处理/明确移除失败项的选择 |
| 评论草稿 | 原生面板或 Web 评论编辑器各自持有；未发表草稿保留或明确提示，不能被“保存正文”隐式发表 |
| 版本恢复 | Web 版本流程；存储恢复与协作房间更新都成功后才完成，其他客户端的显示和继续编辑一并验收 |

不引入“放弃修改即撤回协作更新”的语义。进程被杀不能依赖异步退出钩子；WebView.saveState/rememberSaveable 也不能恢复内存中的 Y.Doc。配置变化避免不必要的画布重建；进程死亡恢复若无已验证的持久化草稿则明确标为能力缺口，不能显示“已恢复全部内容”。

**C. 账号与会话切换**

- 身份边界采用环境 + realm + 稳定用户标识 + 会话代次。当前使用 meet 用户 UUID（资料未加载时暂用登录手机号；身份补齐会重新建立代次），不使用会随续期变化的 access token 字符串作为身份。登出先推进代次并停止请求/轮询，再清理两套 Cookie、页面状态和媒体缓存；清理完成后才允许新账号进入 docs。
- 引导、API 和媒体响应落地前校验代次，过期响应不得写 CookieJar/store/StateFlow。单飞 mutex 仅解决并发引导，不能单独阻止退出后的旧响应回填。
- 当前加密会话存储不是完整账号隔离证明；Coil 缓存也不能只按附件 URL 复用。媒体只向明确授权的来源附带凭据；外域媒体另定义鉴权方式，不扩展发送 docs Cookie。

**D. 刷新与内容保真**

- 当前30秒刷新是已实现基线；下一步限定为原生页面真实可见且当前账号有效时运行。编辑画布覆盖阅读页、应用后台或网络不可用时暂停；评论面板只刷新可见线程数据。
- 多次手动刷新/返回刷新合并为一次在途请求和必要的一次尾随刷新，防止互斥锁直接丢掉编辑后刷新意图。连续失败指数退避，429 遵守 Retry-After；显式刷新允许立即重试。
- 长文按 block ID 保持可见位置/选择，不把每次轮询变化都做打断式 Toast；明显结构变化或用户选中文字时显示“有更新”供主动应用。
- 不用文档 updated_at 代替正文版本。若新增条件读取，校验值必须覆盖存储正文版本、输出格式和转换器版本；鉴权在返回304前执行，未知/缺失版本时完整读取。先测转换延迟与调用量，再决定缓存或后端事件通知是否值得投入。

**E. 重试、权限与功能回退**

- 按接口记录请求/响应形状、分页、abilities、错误和幂等性：accesses 是数组，invitations 是分页对象，versions 是 marker 分页；不得统一套普通 page 模型。
- GET 可退避重试；创建/邀请/评论等写请求超时后属于结果未知，先刷新确认或使用服务端支持的幂等键，不能自动重复发表。表情的 user_already_reacted 兼容分支仅适用于该明确响应，不推广为通用400重试。
- 协程取消继续抛出，避免切页面后显示失败或旧响应写入新页面。UI abilities 仅控制入口，服务端仍裁决每次写入；失权后清正文和媒体可见状态，邀请与移动改变继承单独验收。
- 原生缺失的富文本评论编辑、审批、复杂块、复制子树等提供可发现的 Web 功能入口；不以删除入口或静默丢格式实现“对齐”。

## 六、风险与决策

| 风险 | 决策 |
|---|---|
| 未收到 dirty 被当作 clean，旧前端或加载期直接退出 | P0；引入未知状态与能力握手，不能以人工部署顺序代替兼容设计 |
| 正文成功被当作全部保存，或销毁页面丢在途修改 | P0；关闭由整体保存协调，失败保留上下文；不承诺“放弃协作修改” |
| 退出账号后引导响应回填旧 Cookie | P0；账号代次、取消与响应校验组成同一生命周期边界 |
| 共享数据库被当作实时权限/内容一致 | 明确快照延迟；权限变更由服务端裁决，页面发现失权后清理内容；编辑房间权限需单独验证 |
| 格式转换故障时 json→markdown 仍依赖同一服务 | 不做重复转换降级；提供明确错误和可用的 Web 入口，Web 也不可用时展示重试 |
| 固定30秒全量转换带来负载与滚动干扰 | 先实施可见性、退避、去重与位置保持；条件请求只在服务端契约成立后引入 |
| 范围持续膨胀：读者原生化变成自研编辑器 | 本轮只完成明确的管理与阅读任务；复杂编辑持续归 Web |

已经确定：采用混合方案、编辑标题归 Web、版本恢复归 Web、不新增票据字段。下一轮实施重点为 P0，发布验证通过后再推进 P1；不再把这些既定事项列为待拍板。
