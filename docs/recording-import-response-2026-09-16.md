# Android 导入结果确认与重试

## 问题

用户报告导入约 20 MB 的 MP4 时反复提示上传失败，但历史录音出现了成功记录；Web 导入正常。

代码检查发现 Android 导入沿用了普通 API 的 30 秒读写超时。后端的 `recording-uploads/` 在校验、计算校验和、写入对象存储和创建记录后才返回 202；客户端停止等待并不会撤销服务端已经接收的请求。原界面把所有异常显示成上传失败，重新选择文件或修改识别参数又会生成新的幂等键，从而可能重复创建记录。

用户随后确认报错约发生在 30 秒后，与此超时路径吻合。尚未获得问题手机的异常日志，不能确认每次失败均为超时。回归测试使用真实本地 HTTP 连接重现服务端延迟返回的路径。

## 修复

- 导入使用独立 HTTP 客户端：读写空闲超时 2 分钟，整次调用最多 10 分钟，普通 API 保持原配置。沿用认证和刷新逻辑，禁止透明网络重试、跳转及缓存。
- 请求结果不明确时提示“文件可能已上传”，提供原地重试和到历史录音查看的指引。
- 不明确的请求保持原幂等键和识别参数；参数暂时禁止修改。重选相同 URI、文件名和大小的文件也保持原请求。明确拒绝且没有之前的不确定请求时可修正参数。
- 幂等范围为当前保留的导入操作；不是跨设备、重新进入页面或不同 URI 的文件内容去重。后端原有键、校验和及配置校验继续生效。

只需更新 Android App，无后端接口或数据库变更。已有重复记录不会自动删除。

## 回归

- `RecordingUploadHttpTest`：相同 multipart 请求延迟 31 秒返回真实 202 JSON，通用客户端出现 `SocketTimeoutException`，导入客户端正常接收并解析成功记录。
- `RecordingUploadRepositoryTest`：原文件流式上传、大小限制、视频后缀、账户隔离和重试参数。
- `RecordingImportPickerTest`：模拟请求已接受但响应超时，验证提示、重选同一视频后的键与参数保留，以及重试成功关闭弹窗并进入记录；保留选择器取消测试。

验证结果：7 项 JVM 测试通过，Android 16 模拟器上 2 项界面用例整组通过（34.214 秒），`checkDesignTokens` 和 `git diff --check` 通过。首次界面测试受同时使用模拟器干扰；用户停止操作后重新完整运行通过。仍需在问题手机上使用原视频验证实际网络和存储耗时。
